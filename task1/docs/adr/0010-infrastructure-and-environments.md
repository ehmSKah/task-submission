# Infrastructure and environments: one CDK stack, typed per-environment config, Floci locally

All AWS resources are defined in **one AWS CDK (Python) stack built from three constructs** (`Identity`, `Data`, `Api`), configured per environment by **one typed config file**. The same code deploys to the Floci emulator locally and unchanged to AWS. Locally, Floci runs in Docker Compose. `make` targets drive everything, and the README documents them as the setup and execution instructions. Secrets are generated by CDK into AWS Secrets Manager and never appear in the repo. The single step outside CDK is seeding test users.

## Decision

**Stack.** `OrdersApi-<env>`, one deployment unit:

| Construct | Resources |
|---|---|
| `Identity` | Cognito user pool; **public** app client (no client secret; auth flows `ALLOW_USER_PASSWORD_AUTH`, `ALLOW_REFRESH_TOKEN_AUTH`; access tokens valid for 15 min); groups `USER`, `ORDER_MANAGER`, `ADMIN`; Secrets Manager secret `/orders-api/<env>/seed-users` (the demo users belong to identity) |
| `Data` | DynamoDB tables `orders` (GSIs `byOwner`, `byCreated`), idempotency (TTL), rate limits (TTL) ([ADR 0005](0005-dynamodb-storage.md), [ADR 0006](0006-rate-limiting.md)); SSM parameter `/orders-api/<env>/rate-limits` |
| `Api` | Authorizer and API functions from one code bundle ([ADR 0009](0009-code-structure.md)); `SpecRestApi` from the OpenAPI document with the AWS extensions added at synth ([ADR 0008](0008-openapi-contract.md)), edge-optimized; Gateway Responses ([ADR 0007](0007-validation-and-errors.md)); explicit Lambda invoke permissions; regional WAF web ACL with the rate-based rule (ADR 0006) |

- **In production, data is protected without a separate stack:**
  - `RETAIN` removal policies on the data
  - deletion protection on `orders`
  - **stack termination protection**

**Environments.** `infra/config/<env>.yaml`, validated by a small Pydantic model, selected with `cdk deploy -c env=<env>`.

| Setting | `local` (Floci) | `aws-dev` / `aws-prod` (real AWS; deployable unchanged) |
|---|---|---|
| Target | Floci, account `000000000000` | real account and region |
| Issuer passed to the authorizer | `http://floci:4566/<poolId>` | `https://cognito-idp.<region>.amazonaws.com/<poolId>` |
| Floci id pinning (`floci:override-id`, `floci:override-cognito-client-id` on the pool) | on, so issuer and client id are deterministic | off |
| Lambda architecture | **host architecture** (auto-detected) | **`arm64`** |
| Removal policy / PITR / deletion and termination protection | destroy / off | `aws-dev`: destroy / off; `aws-prod`: retain / on |
| Rate-limit config cache TTL | 2 s | `aws-dev`: 2 s; `aws-prod`: 60 s |
| `seedUsers` | `true` | `aws-dev`: `true`; `aws-prod`: `false` |
| `testFixtures` (foreign pool, untrusted and short-lived clients, counter-reset helper; [ADR 0011](0011-testing-strategy.md)) | `true` | `aws-dev`: `true`; `aws-prod`: `false` |
| WAF | deployed, not enforced | enforced |
| Log level | DEBUG | INFO |

- **One local deployment serves every test suite.** Suites that need particular limits (tiny limits for `429` tests, high limits for Schemathesis) switch the SSM rate-limit parameter at runtime and wait for the 2-second cache. That also demonstrates ADR 0006's runtime configuration. As a result, such suites run one after another, not in parallel.

**Secrets.** The design is **almost secret-free by construction**:
- DynamoDB access uses IAM roles.
- Tokens are verified with the provider's public keys.
- The Cognito client has no secret.
- CI would obtain AWS credentials through **GitHub OIDC**, not stored keys.

For the secrets that do exist:
- **Today:** the seeded users' passwords.
- **Later:** a cursor-signing key.

Rules:
- **AWS Secrets Manager**, values **generated by CDK** (`generateSecretString`). No secret value exists in git, in config files or in templates.
- **Config refers to secrets by name.**
- **Lambdas read secrets at runtime** through Powertools Parameters (`get_secret`) with caching, never through environment variables.

**Local runtime** (`task1/docker-compose.yml`):
- **Image:** `floci/floci:2.3.0`, pinned.
- **Networking:** `FLOCI_HOSTNAME=floci` and a shared Compose network for Floci's Lambda containers, so the token issuer and its discovery/JWKS URLs are reachable from the authorizer.
- **Docker socket** mounted, because Floci runs Lambda functions as containers.
- **Storage:** `memory`. Every `make up` deploys and seeds from scratch. `persistent` mode is optional.
- **Short-lived tokens:** `FLOCI_SERVICES_COGNITO_ENFORCE_TOKEN_VALIDITY_LIMITS=false`, so expiry tests can use them.
- **Swagger UI** runs under the `docs` profile on `localhost:8080`.

**Workflow** (`make`; the README documents these as the setup and execution instructions):

| Target | Does |
|---|---|
| `make doctor` | checks Docker (with Compose), `make`, `uv` and Node and their versions, and names anything missing |
| `make up` | starts Floci and waits for it; `cdk bootstrap` (idempotent); builds the bundle; `cdk deploy --method=direct -c env=local`; seeds users; writes and prints the local API URL |
| `make token ROLE=user\|manager\|admin` | prints an access token for a seeded user |
| `make test` / `make test-integration` / `make contract-test` | unit / Floci integration / Schemathesis |
| `make lint` | Ruff, mypy, import-linter, OpenAPI lint |
| `make docs` | Swagger UI |
| `make down` | stops everything and removes its volumes |

- **Deploying:** `--method=direct` always. Floci breaks CDK's default change-set redeploys.
- **The local API URL:** the REST API id can't be pinned, so after each deploy a script reads the stack output `ApiId` and writes `http://localhost:4566/restapis/<id>/<stage>/_user_request_` to `build/endpoints.json` for tests and humans. CDK's `api.url` output is the AWS form and isn't used locally.
- **Bundling:** `uv export`, then `uv pip install --target build/lambda --python-platform <arch>-manylinux… --only-binary :all:`. CDK then uses `Code.from_asset("build/lambda")`. No Docker is needed for building, and the target architecture is one flag.
- **Prerequisites** are host tools documented in the README with exact versions: Docker with Compose, `make`, `uv` (it installs Python 3.13 itself) and Node for the CDK CLI, pinned in `infra/package.json` with its lockfile. Python is pinned in `.python-version`.

**Seeding test users** (`make seed`, run by `make up`; the one step outside CDK, because CloudFormation can't set Cognito user passwords):

| User | Group | Purpose |
|---|---|---|
| `alice@example.test` | `USER` | an owner |
| `bob@example.test` | `USER` | a second owner, for isolation tests |
| `manager@example.test` | `ORDER_MANAGER` | read all, change any status |
| `admin@example.test` | `ADMIN` | delete |
| `nobody@example.test` | none | a valid token without a role → `403` |

- **Steps:** `AdminCreateUser` (no invitation), `AdminSetUserPassword` (permanent), `AdminAddUserToGroup`.
- **Passwords** come from the generated secret: one generated password shared by the demo users. Secrets Manager's generator produces a single value per secret, and separate passwords per demo user would add secrets without protecting anything.
- **Idempotent:** existing users are left alone.
- **Guarded:** the script **refuses to run when the environment has `seedUsers: false`**.

## Considered options

- **One flat stack.** The same deployment unit, but without visible identity/data/API boundaries, so a later split would mean restructuring.
- **Separate stacks by lifecycle** (`IdentityStack`, `DataStack`, `ApiStack`). This is the classic separation of stateful and stateless resources.
  - *Against:* CloudFormation exports/imports cause the "deadly embrace" (an export can't change while it is imported). On Floci, adding a GSI destroys `DataStack` and therefore `ApiStack` anyway.
  - *Verdict:* this is the evolution once parts deploy at different cadences or by different teams, passing values through SSM parameters rather than exports.
- **One stack per test suite** (tiny limits, high limits). Three near-identical deployments, where switching the runtime SSM parameter achieves the same.
- **SSM `SecureString` for secrets.** CloudFormation can't create `SecureString` parameters, so they would have to be set outside CDK, with no generation and no rotation.
- **`.env` files / Lambda environment variables for secrets.** Values end up in files and in the function configuration, and they drift between local and AWS.
- **A Cognito client with a secret.** It would add `SECRET_HASH` to every sign-in without protecting anything this API does.
- **arm64 locally as well.** On an x86 machine Floci runs the host's architecture, so arm64-bundled native wheels (`cryptography`) would fail without emulation.
- **CDK Docker bundling** (SAM build image). It needs Docker for building, an image per architecture, and is slower.
- **A toolbox container** (Python, uv, Node and the CDK CLI in an image, so reviewers need only Docker and `make`). A nicer first run, but more to build and maintain than the deliverable (a README with setup and execution instructions) requires. A possible improvement.
- **A CDK custom resource for seeding.** It would keep everything in CDK, at the cost of more code and a path that is less proven on Floci than plain API calls.

## Consequences

- **Local and AWS bundles differ in architecture.** Local bundles target the host; AWS bundles target arm64. CI builds each for its target.
- **Test suites that change the rate-limit parameter run one after another** against the single local deployment.
- **Floci specifics live in the `local` config and the Makefile:** the pinned pool id and issuer base (`flociUserPoolId`, `flociIssuerBaseUrl`), `--method=direct`, the URL lookup, `FLOCI_HOSTNAME`, the token-validity flag. The CDK code only reacts to whether those settings are present.
- **Password sign-in** (`USER_PASSWORD_AUTH`) is for the demo and the tests. Real users would sign in through the hosted login with authorization code + PKCE, or SRP.
- **Deploying to AWS** is supported: `aws-dev` can be deployed, tested with the same suites and destroyed, either locally or through a manually triggered workflow ([ADR 0011](0011-testing-strategy.md)). It is optional and not required for the local deliverable.
- **To verify while building:**
  - the Floci setting that puts Lambda containers on the Compose network
  - that `AWS::SecretsManager::Secret` with `GenerateSecretString` works on Floci (supported in source, not yet run)
