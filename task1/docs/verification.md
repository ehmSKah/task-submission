# Verification of design assumptions

Some design decisions rest on emulator or AWS behaviour that was read in source code or
documentation before it could be run. Each such assumption is a row here, with the check that
proves it. The ADRs link here for the status rather than repeating it. If a check fails, the ADR
it comes from is revisited (amended or superseded).

**How to read the tables:**
- **Assumption:** the behaviour relied on, and the ADR that relies on it.
- **Target:** `Floci` (the emulator, pinned in `docker-compose.yml`), `AWS`, or `Local` (no
  emulator: unit tier or a throwaway probe on the workstation).
- **How it's checked:** the test (`file::test`), the make target, or the step done by hand.
- **Status:**
  - `verified`: the check passed on that target.
  - `failed`: the target behaves differently from what was assumed. The row names the
    workaround, and the design no longer depends on the assumption. All six are places where
    Floci deviates from AWS.
  - `pending`: not run yet.
- **Version / date:** what the check last ran against, and when; `—` while pending.

**State on 2026-10-18:** 102 assumptions: 57 `verified`, 6 `failed` (each with its
workaround), 39 `pending`.
- **35 of the pending rows need AWS and have not yet been run on AWS.** They stay
  `pending` until the first deploy to `aws-dev` (`make up`, `make test-integration` and
  `make contract-test` with `ENV=aws-dev`, or the `aws-e2e` workflow), which fills them in.
  Most are executable `aws_only` or integration tests; a few are done by hand.
- **3** need a gateway failure that can't be triggered against the local stack yet.
- **1** is a check by hand in a browser: Swagger UI's "Try it out" against Floci.
